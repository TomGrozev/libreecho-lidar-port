## 1. Audio
- **Profile format/consumers**: key=value, `schema=1`, `target_id`, `speaker_chain`, `codec_profile`, `hp_driver_gain` (0..35), `pre_gain_db` (0..12), `bass_makeup_db` (0..6); rendered deterministically from `libreecho_platform_targets.py:13-40,56-65` (mt8163-arm32). Only the engine reads it (`airplay/audio_engine.c:56-57,1820-1965`), from `/etc/libreecho/audio-profile` then `/proc/1/root/...`. Missing/short profile falls back to Radar defaults; only an exact `target_id=biscuit` legacy fallback exists (1966-1980).
- **Gate**: `audio_profile_present()` = file exists (`libreecho-init:2133-2135,2308`; `libreecho-generation-transaction:354-380`; `libreecho-reconcile-features:337-360`). Init drops `waked` from the graph when absent (`libreecho-init:2233-2240`); transaction skips wakeword/assistant probes; reconcile skips the services; OTA health uses `assistant_required` (`libreecho-init:3285-3300`, test `test_ota_v3_audio_profile_gate.py`). So adding a valid profile is sufficient to restart waked/agentd (plus payloads/integration bits).
- **audiod needs**: tinyalsa card 0, device 23 (`audio_engine.c:59-61,2340-2360`), output 48 kHz stereo S16_LE, opportunistically S32_LE/24-bit (2300-2337); controls `MFP Gpio Mute`, `Ext_Speaker_Amp_Switch`, `Audio_DacMux_Setting`, `Board Channel Config`, `Right Channel Only`, `HP DAC Playback Switch`, `HPL/HPR Output Mixer *`, `HP Driver Gain Volume`, `Speaker Codec Profile` (Radar/Flat), and `PCM Playback Volume` must read 127/127 (695-810). Speaker tuning is compiled in (`speaker_dsp.h` Radar EQ/MBCL, `biscuit_speaker_dsp.h`), selected by profile; no runtime EQ file.
- **Target definitions**: radar_puffin and biscuit are the only entries (mt8163-arm32 table:24-38); Lidar's table has `audio: None` and the builder writes no profile (`mt8167-arm64/README.md:31`, `mt8167-arm64/libreecho_platform_targets.py:54`, verifier fails if present `mt8167-arm64/verify_recovery_image.py:348-349`).
- **Lidar DT already has** four TLV320ADC3101s on i2c0 (0x18-0x1b, `libreecho-lidar.dts:477-513`) and the TLV320AIC32x4 on i2c2 (0x18, reset GPIO10, MFP5 amp mute, 521-539), but the defconfig has only codecs — no MT8167 AFE/machine card (`mt8167_arm64_defconfig:79-86`). `[INFERENCE]` Phase 6 must add the machine driver and choose a Lidar speaker chain/profile; the engine's mixer names are MT8163-specific and will need a Lidar variant or matching controls.

## 2. Microphones
- micd opens capture **card 0, device 24, 9 channels, 16000 Hz, S24_3LE, 640×4 periods** (documented in `sendspin/hotstage/le_latency_cap.c:5-12,44-57`); channels 7/8 are electrical AEC references (`sendspin/hotstage/README.md:14`, `sync_two_way.py:10`). Channel order/geometry is otherwise in the closed UI source `[INFERENCE]`.
- Calibration: wakeword manifest records `microphone_calibration: idme-q14` (`build_recovery_image.py:2079`); the kernel IDME driver exposes `/proc/idme/*` properties incl. sensorcal/alscal (`Platform/drivers/misc/idme.c:21-27,330-396`). No mic-cal table is shipped in the tools; `[INFERENCE]` micd reads IDME-derived per-unit gains.
- Dependencies: waked requires `-S /run/libreecho/mic.sock` before start (`libreecho-waked.init:19,111-135`) and uses the AEC reference socket `/run/libreecho-audio/aec-reference.sock`; agentd needs the audio socket and mic graph. OTA/graph treat mic and wakeword as one unit (Q1).

## 3. LEDs
- ledd consumes the LED daemon protocol on `/run/libreecho/led.sock` (`audio_engine.c:58`; commands/status in `emulation/hwsim/le_hwsim/adapters.py:88-120`: set_colour/set_brightness/pattern/visualizer/meter/sleep_light...). The MT8163/Lidar path is **not** per-channel `/sys/class/leds`; it is the I2C-device `frame`/`scaled_frame`/`boot_animation` attributes of the IS31FL3236 (`LibreEcho-Linux/drivers/leds/leds-is31fl32xx.c:360-523`; contract test `drivers/leds/test_is31fl3236_scaled_frame_contract.py`). `scaled_frame` is 36 PWM + 36 current-scale bytes (144 hex chars), offset applied by DT `channel-offset`.
- Configuration: Lidar `is31fl3236@3f`, `channel-offset=<3>`, `play-boot-animation`, 12 RGB child LEDs labelled `ringN:{red,green,blue}` (`libreecho-lidar.dts:400-433`); radar_puffin matches (`arch/arm/...dts:1664-1668`). MT8163 has a separate vendor `leds-is31fl3236.c` (`Platform/drivers/leds`), LP55231 disabled on radar and lp855x at 0x2c. `[INFERENCE]` ledd finds the controller by I2C path/name; Lidar's node/address/channel-offset already match, so no userspace change if the device path resolves the same.

## 4. Buttons and privacy
- buttond is an evdev consumer of the gpio-keys/PIC keys and the graph starts it unconditionally (`libreecho-init:2213-2226`). Lidar DT key map (`libreecho-lidar.dts:141-196`): volume GPIO7/12 (`KEY_VOLUMEUP/DOWN`), action GPIO42 (`KEY_HELP`), mic-mute GPIO108 (`KEY_MICMUTE`), privacy switch GPIO18 (`EV_SW SW_MUTE_DEVICE`). MT8163 additionally has the PMIC key as the mute button (`arch/arm/...dts:1139`).
- Privacy ABI (`LibreEcho-Linux/drivers/misc/amz_privacy.c`): platform device from DT node `amz_privacy` (`arch/arm/...dts:3156`), attributes `privacy_trigger` (w, 1 enters only), `privacy_state` (ro 0/1), `privacy_timer_on`, `shutdown_dialog_state`, `power_button_state`, `mute_lamp` (0664) (570-586). Kernel itself toggles on `KEY_MUTE` from `mtk-pmic-keys` (222-300); software cannot leave the latch. Mute lamp drives the privacy GPIO + bright-state line (81-90), refused while latched (533-568). Lidar DT does not yet include an `amz_privacy` node and has no PMIC/`mtk-pmic-keys` `[INFERENCE]`; Phase 6 must add a privacy platform node or the same latch/state interface unless the switch is handled purely as `SW_MUTE_DEVICE`.

## 5. Wi-Fi
- Client plane: interface `wlan0`; `wpa_supplicant -Dnl80211,wext -c <conf>`, then udhcpc (`initramfs/libreecho-wifi:1-70`). Profile precedence: `/data/libreecho/config/wpa_supplicant.conf` (persisted, 0600) then `/etc/wifi/wpa_supplicant.conf`; `ctrl_interface=/tmp/wpa_ctrl`, `update_config=1` (`libreecho-init:1290-1330`, `wpa_supplicant.conf.example:1-5`, `build/prepare-public-wifi-config.sh`). networkd attaches to that supplicant control socket (`ui/README.md:29-33`).
- Driver/firmware (MT8163): whole stack is built-in (`CONFIG_MTK_MT8163_CONSYS`, `MTK_COMBO_BT/WIFI_ANTENNA`, `CFG80211_WEXT`, `mt8163_arm32_defconfig:64-70`), no modules. Radio bring-up in init is the WMT choreography: `wmt_stock_compat --firmware-dir /lib/firmware`, `wmt_launcher --once`, write `1` to `/dev/wmtWifi`, wait for `wlan0` (≤30 s), record `/run/libreecho/wlan0-ready`, then start the client (`libreecho-init:1350-1425`).
- Firmware import: `/usr/local/sbin/libreecho-vendor-import` mounts stock `system_a` (`/dev/mmcblk0p13`) read-only, probes only four Android firmware layouts, hash-pins the 4 MT8163 WMT/Wi-Fi blobs and installs them to `/lib/firmware` (0600), creating `WIFI_RAM_CODE` alias; `/etc/firmware -> ../lib/firmware` (`vendor-assets/README.md`, importer:1-95,140+). On Lidar it reports `state=not-applicable` and exits 0 (`libreecho-vendor-import:85-93,461`; `libreecho-init:1071-1112`), leaving `VENDOR_ASSETS_OK=0`.
- Failure marker: `/run/libreecho/wifi-worker-failed` is written by `wifi_worker_record_failure` for the worker's terminal rc (4 when vendor assets unavailable) (`libreecho-init:1258-1275,1430-1470`); recovery graph waits on it (`recovery_radio_ready_wait:1276-1307`). On Lidar today `start_wifi_network` returns 4 immediately because `VENDOR_ASSETS_OK != 1`.
- Provisioning a running unit: no wpa_cli is shipped (wpa config only sets `CONFIG_CTRL_IFACE`, `wpa-supplicant-2.10.config`). Real path is the web/networkd socket API (`network.sock` commands `scan`, `connect`, `set_hostname`, recovery_* — `emulation/hwsim/le_hwsim/adapters.py:121-150`), which drives `wpa_ctrl`; alternatively write the 0600 persisted profile and reboot (`libreecho-init:1290-1315`). `[INFERENCE]`
- Lidar: DT already has MSDC2 SDIO with switched 3.3 V (`libreecho-lidar.dts:222-235`) and `btmtksdio`/`CFG80211` in defconfig; no MT7668 WLAN driver or firmware path exists in our tree — Phase 6 must port them from `reference/lidar-mainline` and replace the MT8163 import/WMT gates for target `lidar`.

## 6. Bluetooth
- btd serves `/run/libreecho/bluetooth.sock` and the web init waits for `/run/libreecho/bluetooth-ready` (`build_recovery_image.py:1160-1190`; `bt` status fields include `hci: hci0`, transport, pairing/classic/LE — `adapters.py:152-189`). MT8163 uses vendor BTIF/combo/BlueZ-HCI built-ins and `/dev/stpbt`,`/dev/stpwmt` (`mt8163_arm32_defconfig:66-68`, `bluetooth-runtime-test.sh:13`). Lidar defconfig only has `CONFIG_BT=y`+`CONFIG_BT_MTKSDIO=y` (`mt8167_arm64_defconfig:20-23`): the out-of-tree MT7668 HCI driver still has to be ported, and firmware has to be provided (vendor-import is not applicable).

## 7. Modules and firmware in images
- Neither image ships `/lib/modules`: MT8163 defconfig sets no `CONFIG_MODULES`/`=m` at all, so drivers are built in; the builder only creates `lib/firmware` dirs (runtime firmware comes from the owner's stock at boot) plus `regulatory.db(.p7s)` (`build_recovery_image.py:743,804-805`). The Lidar builder reuses ARM32 staging and explicitly refuses `--wifi-dtb`/`--connectivity-bundle`/`--audio-probe` MT8163 payloads; it writes no audio profile (`mt8167-arm64/README.md:31,120-135`). So there is no module path on either target; Phase 6 drivers must be built-in (6.18 LTS).

## 8. UI
- "The UI" is the separate `LibreEcho-UI` repo (not cloned here): web app plus the ARM32 hardware daemons it builds (audiod, micd, ledd, buttond, btd, networkd, logd, timed, timerd, watchdogd, radiod, airplayd, esphomed, mdnsd, wyoming STT/TTS clients) staged by `ui/build_ui_bundle.sh:450-530`; the image starts them via `/etc/init.d/libreecho-*.init` (`ui/README.md:19-40,79-84`). Hardware touched: ALSA (audio/mic), LED sysfs/I2C, evdev, wpa_supplicant, BlueZ, privacy sysfs, plus TLS/Opus for web/radio. Validating on Lidar = build the bundle for armv7 musl, boot it, and verify each daemon's socket + real device path (audio card/PCM, mic.sock capture, led.sock frame write, key events, wlan0/hci0, privacy attributes) via `hwsim` first then on hardware (`emulation/hwsim/README.md`).

## 9. OTA confirm/health
- Base required services in production: `networkd` (network.sock), `audiod` (audio.sock), `micd` (mic.sock), `btd` (bluetooth.sock), checked by pidfile+socket owner (`libreecho-init:3200-3240`). Then optional `airplayd`, shared mDNS, `ledd` handoff; HA mode requires `esphomed` and returns; otherwise STT/TTS sockets and — only when `assistant_required` (audio profile present and integration bit 0 clear) — `agentd`; a voice-free remote/diagnostic config may pass without the voice graph (`libreecho-init:3255-3310`). `libreecho-generation-transaction:354-380` probes airplay2/tts/wakeword/stt/assistant with the same audio gate. Consequently: on MT8163, adding a profile makes wakeword+agentd required; on Lidar today they are skipped, so Phase 6 must supply the profile *and* make those services actually healthy or OTA rollback will start. Startup-ready marker (`/run/libreecho/startup-ready`) is required unless `HEALTH_STRICT_SERVICES=0` (the current default confirms on the recovery plane alone) (`libreecho-init:3340-3365`).

## 10. Other per-target hardware hooks
- Ambient light: MT8163 uses the vendor IIO drivers in the Platform tree (`CONFIG_ALS_TSL2583/TSL2584_AUTOZERO/TSL2540/AMZN_AMS_ALS`, `mt8163_arm32_defconfig:139-145`); Lidar's copied drivers expose `als_lux`, `als_lux_table`, `als_power_state`, `als_auto_gain`, `als_gain`, `als_cpl`, `als_persist`, `als_itime`, `als_wtime` (`LibreEcho-Linux/drivers/iio/light/libreecho/ams_tsl2540_als.c:449-788`), with per-unit calibration from `/idme/alscal` (`ams_tsl2540.c:547-576`). Lidar DT does not yet instantiate a light sensor `[INFERENCE]`; ledd idles/night mode is the likely consumer.
- Thermal: MT8163 builds `CONFIG_THERMAL`, CPU_THERMAL and `CONFIG_SENSORS_TMP103` (`mt8163_arm32_defconfig:96-99`); Lidar's defconfig has no thermal zone `[INFERENCE]` besides the watchdog, so the runtime's thermal/timed hooks have nothing to read until a TMP103/thermal zone node is added. Thermal is not part of the OTA health set.
- Reboot/recovery is already per-target: Lidar uses syscon-reboot-mode on TOPRGU (`libreecho-lidar.dts:585-599`) and `libreecho-bootctl`; the privacy `power_button_state` attribute is the only other board hook the runtime may poll.
